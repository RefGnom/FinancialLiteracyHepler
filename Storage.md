# Модуль хранения данных

## Назначение

Модуль отвечает за физическое хранение, извлечение, резервное копирование и восстановление всех доменных сущностей. Реализует интерфейсы репозиториев, определённые в проекте `Domain`, с использованием реляционной СУБД. Начальная реализация – SQLite. Архитектура позволяет в будущем заменить СУБД на PostgreSQL без изменения доменного кода.

Имеется возможность переключить СУБД с SQLite на PostgreSQL путём указания настройки

## Архитектурное расположение
- Проект: `FinancialDiscipline.Infrastructure`
- Зависимости:
  - `FinancialDiscipline.Domain` (интерфейсы репозиториев, доменные модели)
  - `FluentMigrator` (миграции)
  - `Microsoft.Data.Sqlite`
  - `Dapper` (для простоты и производительности)

## Требования к хранилищу

### Общие
- Данные хранятся локально в файле `finance.db` в каталоге `%APPDATA%\FinancialDiscipline\`.
- Поддерживается транзакционность (BEGIN/COMMIT/ROLLBACK).
- Все операции с БД логируются (уровень Debug в Serilog).
- При первом запуске база создаётся автоматически, миграции накатываются до последней версии.
- Индексы создаются для полей, по которым часто фильтруют: Date, AccountId, CategoryId, ScopeId, IsDeleted, FromTransactionId, ToTransactionId, TransactionType.
- Пакетная вставка: при импорте больших файлов транзакции добавляются пачками по 1000 записей в одной транзакции БД для ускорения.

## Отличие хранимых сущностей от доменных моделей

Доменные модели (в `Domain`) содержат бизнес-логику, поведение, инварианты. Хранимые сущности (в `Infrastructure`) – это простые DBO с публичными геттерами/сеттерами, отражающие структуру таблиц БД. Они не содержат методов и бизнес-правил.

### Основные различия

1. **Тип транзакции**:
   - В домене поле `TransactionType` отсутствует (оно вычисляется по правилам из суммы и наличия связей InternalTransfer).
   - В хранимой сущности поле `TransactionType` присутствует как вычисляемое при сохранении (хранится в БД для быстрой фильтрации). Значение пересчитывается перед вставкой или обновлением на основе доменного состояния.

2. **Связи**:
   - Доменная `Transaction` содержит коллекции `Positions`, `Tags`, список `CompensationLink`, `ScopeId`. Это полноценные объекты.
   - Хранимая сущность `TransactionDbo` содержит только `Id` и `ScopeId` (внешние ключи). Позиции хранятся в отдельной таблице, теги – через связь многие-ко-многим, компенсации – в отдельной таблице, внутренние переводы – в отдельной таблице.

3. **Мягкое удаление**:
   - В домене флаг `IsDeleted` есть, но методы `Delete()` и `Restore()` изменяют его и обновляют `UpdatedAt`.
   - В хранимых сущностях `IsDeleted` – просто поле (0/1). При загрузке по умолчанию оно игнорируется, если в фильтре не указано `includeDeleted = true`.

4. **Расширяемые метаданные**:
   - Домен содержит `Dictionary<string, string> Metadata`.
   - В хранимой сущности это поле сериализуется в JSON-строку (в SQLite – текст).

5. **Иерархия категорий**:
   - Доменная `Category` имеет ссылку на родителя (`ParentId`), но не содержит список детей.
   - Хранимая сущность `CategoryDbo` аналогична.

6. **Компенсации**:
   - Доменная `Transaction` содержит коллекцию `CompensationLink` (объекты с полями `FromTransactionId`, `ToTransactionId`, `Amount`).
   - В БД это отдельная таблица `Compensations`. При сохранении транзакции список компенсаций синхронизируется с таблицей.

7. **Внутренние переводы**:
   - Доменный `InternalTransfer` не имеет собственной сущности; связь двух транзакций как InternalTransfer хранится в отдельной таблице `InternalTransfers`. В домене тип транзакции определяется по наличию такой записи.

## Схема базы данных (основные таблицы и поля)

### Таблица `transactions`
- `Id` (TEXT, PK)
- `Date` (TEXT, ISO8601) – дата операции
- `Amount` (DECIMAL) – сумма
- `Description` (TEXT)
- `Comment` (TEXT, nullable)
- `AccountId` (TEXT, nullable)
- `CategoryId` (TEXT, nullable, FK → Categories.Id)
- `ScopeId` (TEXT, nullable, FK → Scopes.Id)
- `IsDeleted` (INTEGER, 0/1)
- `CreatedAt` (TEXT)
- `UpdatedAt` (TEXT)
- `IsForeignCurrency` (INTEGER, 0/1)
- `Metadata` (TEXT, JSON)
- `TransactionType` (TEXT, не NULL) – вычисляемое поле: 'Income', 'Expense', 'InternalTransfer'

### Таблица `Positions`
- `Id` (TEXT, PK)
- `TransactionId` (TEXT, FK → Transactions)
- `Name` (TEXT)
- `Amount` (DECIMAL)
- `CategoryId` (TEXT, nullable, FK → Categories)
- `Comment` (TEXT, nullable)
- `IsDeleted` (INTEGER, 0/1)

### Таблица `Tags`
- `Id` (TEXT, PK)
- `Name` (TEXT, UNIQUE)

### Таблица `TransactionTag` (связь многие-ко-многим)
- `Id` (TEXT, PK)
- `TransactionId` (TEXT, FK → Transactions)
- `TagId` (TEXT, FK → Tags)

### Таблица `PositionTag` (связь многие-ко-многим)
- `Id` (TEXT, PK)
- `PositionId` (TEXT, FK → Positions)
- `TagId` (TEXT, FK → Tags)

### Таблица `Categories`
- `Id` (TEXT, PK)
- `Name` (TEXT)
- `ParentId` (TEXT, nullable, FK → Categories)
- `Description` (TEXT, nullable)

### Таблица `Scopes`
- `Id` (TEXT, PK)
- `Name` (TEXT)
- `Description` (TEXT, nullable)

### Таблица `Compensations`
- `Id` (TEXT, PK)
- `FromTransactionId` (TEXT, FK → Transactions)
- `ToTransactionId` (TEXT, FK → Transactions)
- `Amount` (DECIMAL)

### Таблица `InternalTransfers`
- `Id` (TEXT, PK)
- `FromTransactionId` (TEXT, UNIQUE, FK → Transactions)
- `ToTransactionId` (TEXT, UNIQUE, FK → Transactions)

## Миграции
- Используется FluentMigrator. Миграции лежат в `Infrastructure/Migrations`.
- Каждая миграция содержит `Up()` и `Down()`.
- При первом запуске приложения миграции накатываются до последней версии.
- Поддержка SQLite и PostgreSQL через условные конструкции (`IfDatabase`).
- Версия схемы хранится в таблице `VersionInfo`.

## Репозитории (реализация)
- Каждый репозиторий реализует интерфейс из `Domain`.
- Использует Dapper для выполнения запросов.
- Преобразование между доменной моделью и хранимыми сущностями осуществляется с помощью маппера.
- Репозиторий не знает о бизнес-правилах – он только читает и пишет данные.

## Транзакционность
- Все операции, изменяющие более одной таблицы (добавление транзакции с позициями и тегами, удаление дубликатов, изменение компенсаций), оборачиваются в транзакцию БД (`BeginTransaction`/`Commit`/`Rollback`).
- При массовом импорте транзакции группируются в пачки (например, по 1000 записей) и каждая пачка сохраняется в отдельной транзакции для баланса производительности и надёжности.

## Бэкап и восстановление

### Создание бэкапа (команда `backup`)
- Создаётся копия файла `finance.db` с именем `finance_backup_DDMMYYYY_HHMMSS.db`.
- Копия сохраняется в папку `%APPDATA%\FinancialDiscipline\backups\`.
- Опционально: перед копированием база данных может быть синхронизирована через `PRAGMA wal_checkpoint` (если используется WAL-режим).

### Восстановление (команда `restore`)
- Пользователь указывает путь к файлу бэкапа (или выбирает из списка в папке `backups`).
- Текущая база данных `finance.db` заменяется на выбранный файл бэкапа (предварительно создаётся резервная копия текущей БД на случай отката).
- Приложение перезапускает соединение с БД.

### Преимущества подхода
- Максимальная простота.
- Сохраняются все индексы, триггеры, настройки.
- Не требуется знать схему для восстановления.
- Работает быстро даже для больших файлов.

### Недостатки
- Привязанность к SQLite (не подходит для будущего перехода на PostgreSQL). Это принимается как временное решение. При миграции на PostgreSQL механизм бэкапа будет изменён на дамп SQL или другой кросс-СУБД формат.

### Альтернатива на будущее (для PostgreSQL)
Когда произойдёт переезд, бэкап будет создаваться через `pg_dump` или через экспорт данных в переносимый формат (например, CSV/JSONL). Пока этот функционал не требуется.

## Логирование
- Все запросы к БД логируются на уровне Debug (через Serilog).
- Ошибки БД – Error.
- Полное логгирование на все сценарии системы
- Достаточное покрытие для расследования ошибок
- Все логи на английском языке

## Обработка ошибок
- Любое исключение SQLite оборачивается в кастомное `DatabaseException` с понятным сообщением (например, "Не удалось сохранить транзакцию: нарушение уникальности тега").
- CLI отображает сообщение пользователю и предлагает действия.
- Все пользовательские ошибки на русском языке

## Переход на PostgreSQL
- Интерфейсы репозиториев остаются неизменными.
- Создаётся реализация `PostgresTransactionRepository` с использованием Npgsql.
- Миграции FluentMigrator уже поддерживают PostgreSQL (типы данных адаптируются автоматически).
- В `settings.json` меняется `Provider` и `ConnectionString`.
- Требуется адаптация в коде маппера (работа с JSON-полями: в PostgreSQL используется тип `jsonb`). Это единственное место, которое потребует изменений в Infrastructure.
